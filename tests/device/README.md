# 実機での固定入力確認

## 準備

1. 対象ソースのcommitと未コミット差分、端末／OS版、SDK版、HAPのSHA256を記録する。
2. `tools/fast-device.ps1 -Build -BuildMode release` でビルドする。署名は開発環境の設定を使う。
3. `tools/fast-device.ps1 -Install -SelectKanon -OpenPreview` で導入・プレビューを開く。
4. 端末を解除し、`pages/PrivatePreview` の入力欄をタップする。欄のIDは `kanon_validation_input`。
5. 各ケース前にこのテスト欄を空にし、日本語／英語とQWERTY／12キー、FULL／BASICを記録する。

複数端末ならfast-deviceの `-Target` を明示する。導入したHAPと実行中IMEの版が一致することも確認する。
FULLとコンテナの比較にはreleaseを使う。製品ブリッジのohosTestは入力欄・UIの受入試験の代わりにしない。
入力欄の初期状態・配列・候補選択操作を固定し、個人の入力内容を再現データに使わない。

## 基本ケース

| ID | 操作 | 合格条件 |
|---|---|---|
| D01 | JP QWERTYでk→i、候補「き」で確定→k→i。5回繰り返す | 新しい「き」に余分なｋ・きが付かない。途中子音も表示される |
| D02 | JP QWERTYでki→Delete | 「き」が消える。ｋに戻らない |
| D03 | JPでten→候補「・」をタップ→ki | 「・」は1回だけ確定し、IME再起動なしで次を入力できる |
| D04 | JPでki→？→ku | 未確定の「き？く」を保持。記号を入れただけで勝手に確定しない |
| D05 | JPでkaki→左矢印→sa→対象候補をタップ | 途中に挿入でき、対象範囲外の後続「き」を保持する |
| D06 | JPでkyouha→変換→左矢印で「きょう」まで縮小→「今日」をタップ→ga | 「今日」だけ確定し、残り「は」と追加入力「が」を保持する |
| D07 | JP 12キーでかな入力→変換→記号候補→追加入力 | QWERTYと同じ確定・後続保持。重複しない |
| D08 | ENでhel→Spaceで候補選択→Enter | Spaceは候補選択、Enterは確定。二重入力しない |
| D09 | 未確定ありで別の入力欄へ移動→新しい入力 | 前の欄の候補や遅い結果を新しい欄に入れない |
| D10 | QWERTY Space長押し・ドラッグ→部分確定→濁点を含む追加入力 | カーソル／範囲が追従し、残りを失わず編集を続けられる |
| D11 | 未確定なしでEnter | 欄のEnterアクションを1回送る。検索欄なら検索する |
| D12 | 背景・キー間隔を保存→入力欄を開く→IME切替で戻る | 保存した値がIMEに反映され、古い状態へ戻らない |
| D13 | ki→Deleteで空→ka | 空になった後の再入力が「か」。余分なｋ・きがない |
| D14 | D05の部分確定→残り「き」を削除→確定済み「傘」を削除→ki | 次の入力が「き」。空の未確定セッションが残らない |
| D15 | JP QWERTYでkaki→入力欄内の先頭をタップ→sa | OSのカーソルが0になったことを確認し、先頭へ「さ」を挿入して「さかき」 |
| D16 | D15のs→aを連続タップ | 先頭でローマ字がまとまり「さかき」。余分なｓや末尾のあがない |
| D17 | 空欄でk→i→k→iを連続タップ | 未確定「きき」。子音の重複・欠落がない |
| D18 | 「かき」をEnterで確定→Spaceで1文字左→gaを入力・確定→Spaceで1文字右→ka | 「かがきか」。確定済み本文への左右移動・途中／末尾挿入が正常 |
| D19 | プレビュー非対応欄でENへ切替→hel→Space→Enter→Delete2回 | Spaceは候補選択だけで本文「hel」、Enterで「hello」、Deleteで補完を戻して「hel」、次で「he」 |
| D20 | 同じ欄のENでhel→候補「hello」をタップ→Delete | 「hello」が1回入り、Deleteで元の「hel」へ戻る |
| D21 | 通常のプレビュー対応欄でENへ切替→hel→Space→Enter→Delete2回 | helloを確定、最初のDeleteでhelの未確定へ復元、次でheへ削除 |
| D22 | JP QWERTYでki→配列切替2回→ka→Enter | 途中の「き」を保持してQWERTYへ戻り、続けた文字と合わせて「きか」。切替は既存の未確定を確定する |

候補選択はラベルで指定し、候補0番という順位には依存しない。
範囲が狙った位置まで縮んだことを、読みと候補欄で確認してから確定する。
ネイティブ欄の下線は、本文／未確定動作の判定と分けて記録する。

## HDCから固定ケースを実行する

```powershell
powershell -NoProfile -File tools/fast-device.ps1 -Target '<接続先>' -OpenPreview
powershell -NoProfile -File tools/test-input-field.ps1 -Target '<接続先>' -Case D14 -PrepareQwerty -PixelsPerVp 3
# Huaweiブラウザの固定ページを開いた後
powershell -NoProfile -File tools/test-input-field.ps1 -Target '<接続先>' -FieldId kanon_web_input -ExpectedMission com.huawei.hmos.browser -Case D14 -PrepareQwerty
```

`native-input-cases.json` のD01／D02／D04／D05／D06／D08／D13／D14／D15／D16／D17／D18を実行できます。
D19／D20は同じプレビュー画面の下段`kanon_validation_direct_input`を`-FieldId`へ渡します。この欄はSDKの`enablePreviewText(false)`を指定しています。D19はJPから開始、D20はENから開始してください。
D21は通常欄`kanon_validation_input`を使い、JPから開始します。D19の直接入力と、同じキー列で表示・復元経路を比較できます。
開始時は日本語モード、D04には12キー有効、D08には英語有効が必要です。`PrepareQwerty` は配列だけを準備し、言語を変更しません。
D08終了後は英語です。3言語すべて有効であることを確認した上で、補助手順 `SETUP_EN_TO_JP` を使えます。
候補はラベルで探します。候補が一意に見つからない場合は停止し、別の候補で代用しません。

SpaceドラッグはUITestの長押し付きdragで24vp動かします。18vpの移動閾値を1回だけ越える距離です。
`PixelsPerVp` は対象端末のpx/vp比で、今回の端末は3です。他端末へ同じ物理px値を流用しません。
途中で配列を切り替えると未確定文字が確定されるため、範囲変更ケースの代わりに使いません。

`OpenPreview` は検証用Wantに限り表示中の自動消灯を抑えます。通常設定画面へ移動、またはアプリが背景へ移ると元の値へ戻します。
固定IDの入力欄を毎操作前に確認し、ロック画面や別画面ではキーを押さず `environment-wait` とします。
前面のmissionも照合します。既定はkanonのプレビューで、Web入力には `ExpectedMission` を明示します。
フォーカス済みの欄を再タップしません。本文をタップする操作は入力欄変更の別ケースとして扱います。
D15は明示的に本文をタップします。`tapXFraction` は対象ノードの横幅に対するタップ位置で、既定は0.5、指定範囲は0より大きく1より小さい値です。
`longPress: true` は同じ位置で長押しします。実際に選択範囲が作られたことは、操作命令の完了と分けて確認します。
手元の端末ではD15の0.06で選択位置0を通知しました。他端末ではフォント・余白によりずれるため、座標だけで同じカーソル位置と断定しません。
途中位置を編集したケースの後はプレビューを開き直し、新しい空欄で実行します。前の欄を先頭位置からDeleteで消し続ける方法では準備できません。
`burst` では同じ検証済みUI配置の2〜16個のQWERTY英字キーを、キー間の待機・UI読み直しを挟まずuinputでタップします。
開始前に全対象キーを照合し、最後の本文を期待値と比較します。各タップの途中表示の保証や描画遅延の測定ではありません。
レポートのburstElapsedMsはHDC往復を含む操作時間です。旧UITest方式と、新しいuinput方式の結果を区別します。
HuaweiブラウザでHTMLのIDがUIツリーへ出ない場合は、固定ページの見出しと同じWeb領域内の固有ラベルで欄を確認します。
この判定は `kanon_web_input`／`kanon_web_textarea` のみで使い、一般の検索欄へ広げません。

結果は `.local/device-validation/<日時>-<case>/report.json` へ保存します。
本文・候補ラベルは固定fixtureに限定し、一般の予測候補は件数だけを記録します。OS版・IMEモード・ケース定義のhashも残します。
`localHapSha256` はPCにあるHAPの識別であり、端末へその版を導入した証明は対応するインストール記録で確認します。
`layout.json` は転送後にキーボードのID・座標と固定入力だけへ絞ります。一般の予測候補や他画面の本文は証拠に残しません。Gitには含めません。

## 入力先ごとの比較

| 入力先 | 固定する対象 | ケース |
|---|---|---|
| Harmonyネイティブ | kanon PrivatePreviewの固定ID欄 | D01〜D10、D12 |
| Web | [input.html](input.html) の単行inputとtextarea | D01〜D06、D08〜D11 |
| EasyAbroad内Chrome | 同じinput.html（ブラウザ／コンテナ版も記録） | D01〜D06、D08〜D11、FULL／BASICを別行で記録 |
| 検索欄 | 問題のあるOS／Chromeの検索欄 | D01、D03、D11。Web fixtureとは別行で記録 |

Web fixtureは専用サーバーで配信し、端末から到達できるURLを開く。

```powershell
node tools/serve-input-fixture.cjs 127.0.0.1 8765
hdc -t '<接続先>' rport tcp:8765 tcp:8765
# Harmony側ブラウザで http://127.0.0.1:8765/input.html を開く
# 終了後はサーバーをCtrl-Cで止め、hdc fport lsに表示された今回の転送だけをhdc fport rmで削除する
# 今回の転送を削除する例（他の転送は削除しない）
hdc -t '<接続先>' fport rm tcp:8765 tcp:8765
```

このサーバーは固定ページだけを返し、他のパスやPOSTを拒否します。
コンテナ側のlocalhostへ転送が届かない場合は、LAN側で配信してPCのIPを使い、到達可否も別に記録します。
ファイルを開く方法・ネットワーク条件も記録する。ブラウザの検索／URL欄とHTML inputは別の入力先として扱う。
fixture自身はネットワーク送信・入力内容のログ記録・文字列の自動補正を行わない。

この段階ではWeb／コンテナ、変換中の選択・範囲選択・未確定外タップを実施していません。P19や他HAPの合格と結果を混ぜません。
