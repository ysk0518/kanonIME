## 調査時の検証画面（製品から撤去済み）

調査 HAP では `EntryAbility` を `kanonEditorSendProbe=true` で起動した。
`pages/EditorSendProbe` はネットワーク通信・実際のメッセージ送信のない専用画面だった。
最終整理でこの画面・起動フラグ・専用の入力側状態機械は製品から撤去した。
同じ比較を再構成する場合は、プレビュー有効の TextArea と、下記2種類のローカル本文消去ボタンを用意する。

| 操作 | 実機での結果 |
|---|---|
| プレビューありで入力 → Send（本文を空にする → stopEditing） | 純正／kanon とも残留。kanon の最新比較でも欄長1 |
| プレビューありで入力 → Finish + Send（stopEditing → 未確定終了の onChange → 本文を空にする） | 純正／kanon とも欄長0。確定後の本文長1を取得してから消せた |
| プレビューなしの直接英語入力 → Send direct | 以前の比較で欄長0 |
| kanon で Discard + Send | 以前の比較で残留。要求の Promise 完了後に IME の消去処理が到達し、フォーカス喪失エラーになった |
| 純正で Discard + Send | 以前の比較で `12800015`（相手側が要求を受け付けない） |

最新の正しい順序の記録（両 IME で一致）:

```text
change bound=0 composing=1
finish-before-clear action=finish
editing value=false
change bound=1 composing=0
clear stop=false bound=1 composing=0
change bound=0 composing=0
```

逆の順序の kanon 記録:

```text
change bound=0 composing=1
clear stop=true bound=0 composing=1
editing value=false
change bound=1 composing=0
```

調査時の `SendAfterComposition` はタイマーではなく、プレビュー終了を示す実際の変更通知を待つ状態機械だった。
調査時はその単体テストを含め479件成功。最終PRでは、この画面専用の4件を外し、外部消去同期の回帰テストを残す。
最終整理後は475件成功、リリースHAPのビルド成功。最終整理後の実アプリ再確認は未実施。
実アプリでの解消は単体テストの成功条件に含めない。

## ここまでで分かること

この検証画面では、本文の消去と未確定の終了の順序で結果が変わる。
未確定文字はバインドされた本文とは別に保持され、本文だけを空にしても消えず、終了後の変更通知で戻る。
IME のローカル候補消去だけでは入力コンポーネントに残った本文は消せない。

Celia では送信時にパネル非表示と入力先エラーを観測したが、明示的な破棄要求は観測できていない。
調査中に試した「非表示＋入力先エラーによるローカル破棄」は最終PRから撤去した。
単なるパネル非表示を送信と見なすことや、再接続時に欄全体を削除することはできない。
入力側の実装を変えられないアプリへの互換対策は別途検討が必要。
未確定表示を使わない方式にも変換・途中編集への影響があり、今回の調査だけで全面変更しない。
