# PCで実行する単体テスト

Node.js 18.20以上を使います。DevEco Studioに同梱されたNode.jsでも実行できます。
初回はこのディレクトリで依存を入れます。

```powershell
cd tests
npm ci --ignore-scripts --no-audit --no-fund
npm test
npm run test:mutations
```

依存の導入後は、プロジェクト直下からも実行できます。

```powershell
node tests/run.cjs
node tests/run.cjs --test-name-pattern "R02:"
node tests/mutations.cjs
```

## CI

[PC tests](../.github/workflows/unit-tests.yml) はPR、mainへのpush、手動実行で動きます。
Windows 2025／Ubuntu 24.04のNode.js 24と、Ubuntu上のDevEco互換Node.js 18.20.1で、
`npm ci --ignore-scripts --no-audit --no-fund` → `npm test` → `npm run test:mutations` を実行します。
正常版の合格に加え、意図的に戻した不具合が期待したアサーションで検出されることを確認します。
テストランナーはNodeの既定レポーターに依存せず、検出チェックで読むTAP形式を指定します。
レポーターの指定は [Node.js公式ドキュメント](https://nodejs.org/api/test.html#test-reporters)、
CIのNode導入・依存導入は [GitHub公式手順](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs) に沿っています。

失敗時はGitHubのPRに表示されるチェック、またはActionsの `PC tests` を開き、
対象OS／Nodeの `Run regression tests`・`Verify mutation detection` のログを確認してください。
検出チェックが正常版で止まった場合は、先に通常テストの失敗を直します。

このCIはSDK・署名・ネイティブライブラリを読み込みません。HAPのビルド、ArkTSの製品型検査、
実Mozc・OS・実機の入力確認は別途行います。チェック名をブランチ保護に登録する作業も別です。
GitHub上での初回実行結果は、この変更をpushしてPRを作成した後に確認します。

## 実行対象

[実機確認](device/README.md) を参照してください。通常のPCテストと結果を分けて記録します。

## 期待値の根拠

テストの合格は、決めた期待値と実装が一致することを示します。
一般的なIMEの操作として適切かどうかは、対象操作・入力例・比較対象のキーボードを決めて別途仕様確認します。
不具合を戻して失敗する確認も、期待値そのものの正しさを証明するものではありません。

- ユーザーと合意した動作: QWERTYのDelete、部分確定後の後続文字保持、Space長押しによる位置・範囲の変更。
- 整合性の契約: 二重確定しない、取消や入力先変更後に新しい操作へ古い結果を適用しない、文字単位を壊さない。
- 現状の暫定値: ドラッグ18vp、タップ許容12vp、1イベント16移動の上限、長押し時点の座標を起点とする扱い、
  追跡起点・カーソルとも不明のとき0へ補う扱い。対応テスト名に `provisional` を付けています。

寸法・候補APIの呼び出し順・失敗時の表示など既存のテストにも実装上の判断が含まれます。
これらを一般的な仕様として承認済みとは扱いません。仕様変更時は根拠とテストの期待値を一緒に更新します。

ローダーはプラットフォームへのimport、動的import、既知のArkUIグローバルを検出した場合に停止します。
HarmonyOSのAPIを空の偽物に置き換えてテストを通すことはしません。
TypeScriptの `transpileModule` はArkTSの型検査・UI構文・製品ビルドの代わりにはなりません。
イベント型テストのみ、製品から取り出した宣言と固定fixtureをTypeScriptの型検査に通します。
アプリ全体の型検査ではありません。受付形UiEventをキュー内で検証・複製し、必須payloadを持つInputEventで内部処理とEnginePortへ渡します。製品全体のArkTS検査は別途リリースビルドで行います。
詳細は[TypeScriptのコンパイラーオプション](https://www.typescriptlang.org/docs/handbook/compiler-options.html)を参照してください。

## 不具合を検出する確認

`mutations.cjs` は通常のテストが通ることを確認した後、次の変更をコンパイラーへ渡す文字列にだけ加えます。
製品ファイルは変更せず、対応するテストのアサーションが失敗した場合のみ検出成功にします。
WindowsのCRLFとLinuxのLFは、対象ソースのメモリ上でLFに揃えてから置換します。
改行形式が異なっても同じ変異を適用し、対象の欠落・重複は引き続き失敗とします。
正常版は毎回全件を実行し、変異版は対応するテスト名のグループを含む全ファイルを実行します。
無関係のグループのロード・コンパイルを省き、80件の変異と検出条件は維持します。
Node 24以降のテストには30秒の期限を付け、故意に処理を壊して通知が来なくても無期限に待ちません。

## 別に確認すること

HarmonyOS SDKによるリリースビルド、実際のMozcとの結合、ネイティブ・Web・コンテナへの入力、
表示・ArkUIのタッチ配送・Watchによる取消は別の確認が必要です。既存の `entry/src/ohosTest` もこのコマンドでは実行しません。
設定の実保存・通知・ACK配送、KanonIme全体の自動テスト、GitHubでのCI初回実行は未確認です。
P02の英語phaseは偽物のEnginePortで契約を確認し、P09は実際のEnglishPrediction・EnglishEngineを使います。
英語のUI通知は偽物のPortへ渡します。実際のAppStorage接続はEnglishRuntimeに限定し、PCテストから除外します。
P18は既存の英語選択方針を分離して実行します。編集中フラグ解除後に遅延した内部通知を受ける場合も、現状の位置不一致の扱いを確認します。
この通知をユーザー操作と証明するテストではありません。同位置の通知からOSプレビュー終了を判別することもできず、日本語への共通適用は未実施です。
P20の日本語同期は英語の破棄方針を共通適用せず、現在の入力欄位置を照会して未変換の未確定内だけを編集します。
P21は未確定表示とカーソル配置の成功を分け、配置失敗後の通知でエンジンの挿入位置を上書きしないことを確認します。
配置成功後の同期再開、古い通知の破棄、入力先変更・表示書き込み失敗も対象です。Web側のカーソル描画を模擬して保証するものではありません。
P22ではPreviewCaretPlacementをSDKなしで実行し、入力欄の既知の未確定範囲内だけを1コードポイントずつ移動します。
位置はUTF-16で検証し、APIエラーは保持して自動再送しません。APIキューの既存期限で取消し、遅い応答後の後続移動を発行しないことも確認します。
カーソル移動にも製品PreviewSelectionReceiptを接続し、通知とAPI応答のどちらが先でも両方を待つこと、別位置の通知では先へ進まず、既存期限で待機を取り消すことを確認します。
実EditorAdapterのタイムアウト通知・入力先変更への配線、各入力欄が実際に1コードポイント移動するかは実機確認と分けます。絵文字の単体試験を全入力先の実機検証と扱いません。
予測候補・確定効果・未確定表示の接続も製品MozcEngine／Coordinator／CompositionPreviewで確認しますが、実SDK接続全体の単体テストではありません。
通知待機は既存APIキューの期限・入力先変更で取消し、期限切れ後にカーソル操作を発行しません。純粋な通知待機モデルの合格と、各入力欄で実通知が配送される確認は区別します。
表示テストは純粋なモデルと偽物の表示Portで実行します。P27では表示入力の収集もImePresentationへ分離し、実英語／日本語エンジンとCoordinatorを接続して確認します。AppStorageへの実書き込みとArkUI描画、KanonIme全体の起動・通知の配線はPCテストの対象外です。候補上限や診断キーの扱いは既存挙動の維持を確認しています。
未確定範囲はCompositionPreviewを通す経路まで確認します。Coordinatorと組み合わせた部分確定のテストもありますが、
KanonIme全体・実EditorAdapter・OSの入力欄を通す確認ではありません。
`provisional` とした位置取得失敗時の0補完は、既存の暫定挙動の記録です。
必須データ検証では欠落、非整数、NaN、不正なモード・端指定を拒否します。
空文字や符号付き候補IDは既存経路に渡します。方向は4つの名前に制限し、端指定との同時指定を拒否します。SDK値との対応は供給する定数を変更して双方向に検査します。実SDKの呼び出し・通知配送と実エンジンの候補ID範囲の検査は別途行います。
直接英語の補完・ローカル要求の処理は、Coordinatorの入口テストだけでは保証しません。
P24では直接英語をDirectEnglishInputへ分離し、実EnglishPrediction・CoordinatorとEditorモデルを接続して実行します。
読み取り中の入力先変更・候補revision更新・範囲選択・予測禁止を制御し、古い候補の補完を拒否することを確認します。
P24時点ではSDKへの接続、属性取得、KanonImeの経路選択全体、Undoの受付・プレビュー復元、配列設定等のローカル要求は別の確認です。
P25ではUndo受付・プレビュー復元・通常英語の補完記録もEnglishCompletionLifecycleへ分離し、実Engine・Coordinator・CompositionPreviewと接続します。
P26はImeLocalRequestsへ配列と貼り付け前確定を分離し、実Coordinator・EnglishEngine・MozcEngine・CompositionPreview・既存入力キューへ接続します。Mozc応答・保存と表示のPortは固定モデルで、実Preferences／CommonEvent／KanonIme全体のPC試験ではありません。
失敗時の本文保持に加え、貼り付け要求自体を送らないことを確認します。下位のrecovery-holdだけで上位の判定漏れが隠れないようにするためです。設定保存の例外は自動再送せず、先に適用済みの配列を巻き戻す仕様は追加していません。
P27のImeRuntimeBindingsは記録用の読み書きPortを使い、ImeLocalRequests・実Coordinator・既存キューと接続します。SDKの入力種別は定数値を外から渡し、番号を仮定しません。AppStorageImeBindingsの実接続はArkTSビルドと固定欄の実機確認で扱います。古い入力先のカーソル結果を破棄するテストは、同じ欄でのあらゆる通知順の保証ではありません。
P28は分離した入力・補完・Undo・未確定範囲・設定接続・候補表示・既存キューを接続して連続操作を確認します。補完Undo→貼り付け、設定保存待ち→追加入力、直接入力→Undo→記号、かなと記号→貼り付け→次の入力、入力先変更、確定失敗を扱います。明示したシナリオのイベントを製品モジュールへ渡し、KanonImeのルーターをコピーしたり、SDK importを偽物へ置き換えたりしません。
テストの既定値と通常の操作仕様の違いは引き続き「期待値の根拠」で区別します。PC、製品ブリッジ、画面上のキー操作は別の確認です。GitHub上のCIはPR公開後の初回実行を確認します。
Editorモデルは新規プレビューによる選択範囲の置換を表現します。SDK全体や選択通知の配送を模擬するものではなく、固定欄の実機結果と区別します。
Spaceで本文を変更しない直接入力の操作、接頭辞40文字・位置4096上限は従来の方針であり、他IMEの一般的な仕様として承認済みとしません。
操作キューは単独のテストに加え、MozcEngine・Coordinator・CompositionPreviewとEditorモデルを接続し、
QWERTYのk→iが未確定表示の完了を待つことを確認しています。ネイティブ接続は固定応答です。
キュー単体は実行中の処理を中断せず、無応答の期限も管理しません。実行中の入力先照合とOS APIの失敗処理は別の責務です。
英語の候補8件上限・40文字制限・初期辞書・候補なしのSpaceの扱いは既存挙動の確認です。
一般的な他IMEとの比較を完了した仕様とは扱いません。補完を戻した後の最終的なOSプレビュー表示と、
KanonImeの直接英語経路・入力先通知全体は未確認です。
設定のテストは実PreferencesやPersistentStorageを使用せず、Modelと移行計算の製品ソースを実行します。
移行前のGSKV読み取り・書き込み・一次保存元の優先順位、移行後の再起動、背景画像の別保存・同期は対象外です。
設定範囲の数値やレコード構造は現在の製品契約を確認しており、設定UIの使いやすさの判断とは別です。
P11では製品のレコード更新計算と保存関数を、時計値・記録用StoragePortで確認します。
Preferences自体やRepository全体を動かすテストではありません。flush失敗時の実ストレージの残り方、
Repositoryのメモリ採用・AppStorage通知、通知の送信・再送・ACK待ちの時間制御は別途確認が必要です。
保存データの比較はJSON内容で行い、実行時のクラスのprototypeは永続化の契約に含めません。
P12は仮想時計と表示・ログの記録用PortでReceiptとRetryの製品コードを実行します。
P12単体では通知配送・送信元フィルター・送受信全体は対象外です。SDK不要の送受信処理はP13で接続して確認します。
再送は初回送信に加えて最大3回、間隔2秒という既存値を維持しています。保存済みはACK受領と同義ではありません。

P13は製品のSettingsSyncCoreを正本／IMEの2インスタンスで接続します。通知は明示的に配送し、
保存は製品のRecordPolicy・Persistenceを使う記録用Port、適用は制御できるコールバックを使います。
CommonEvent接続と実Preferences、KeyboardControllerの実適用・再起動は対象外です。
P12単体では対象外だった送信元フィルター・受信／保存キュー・送受信プロトコルの正常・失敗経路をここで確認します。
仮想時計と有限のPromiseチェーンの処理で同期し、実時間のsleepは使いません。

P15は固定Web入力ページの配信範囲と送信拒否を確認します。P16はPreviewLifecycleの「空への置換→終了」、失敗時の停止、入力先世代の照合を確認します。
Editorモデルでは空のプレビューもセッションを保持します。実機で発見した部分確定後の全削除・再入力は [D14](device/README.md) で別途確認します。

P17は製品EditorOperationQueueへ仮想時計・遅延Promise・固定クライアントを渡し、SDKを読み込みません。
APIを発行する前と完了した後の世代、書き込みの期限切れから遅い完了、エラーと空の読み取り、読み書きのFIFOを確認します。
PreviewLifecycleも接続し、古い欄のclear完了で新しい欄のfinishが呼ばれないことを確認します。
EditorAdapterのSDK呼び出し・選択通知・エラーコード取得の実接続、OSへ発行済みの処理の取消、描画結果はこの単体試験の対象外です。
3000msは現在の実装値を維持したテストであり、他IMEとの比較を完了した期限の推奨値ではありません。
